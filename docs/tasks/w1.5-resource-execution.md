# W1.5 — Execution breakdown (agent-ready)

**Baseline:** 2026-10-12 · **Source of truth for numerical hypotheses:** [06-resource-envelope](../06-resource-envelope.md). **Decisions/status:** [07-roadmap-decisions](../07-roadmap-decisions.md).

## Execution convention

- Task level: `W1.5.C`. First subtask level: `W1.5.C1`; optional second level: `W1.5.C1.a`. **No deeper nesting.**
- Each task requires **input → subtask output → acceptance/DoD → evidence → status**. Only introduce second-level subtasks when they produce distinct evidence.
- `DOCUMENTED` means design written and linked to requirements; **does not mean benchmark passed**. `VALIDATED` requires results from a reproducible harness.
- Execute tasks in order `C/D → E → F/G → H → I → J`, respecting dependencies. A/B are documented input, not measured facts. Every result should update docs/06 and decision register docs/07; tests belong to W1.7.
- `MUST propuesto`/`TARGET`/`STRESS` remain hypothesis categories, not hardware certifications.

## W1.5.C — Compute & Memory Envelope

**State:** DOCUMENTED (provisional budget), empirical VALIDATION PENDING. **Inputs:** A/B, [architecture](../03-logical-architecture.md), [failure invariants](../04-failure-offline-contract.md).

- **C1 — Load model** [DOCUMENTED]
  - **C1.a:** derive routing packets/sec from Ethernet line rate and frame size (64/512/1500 B); distinguish dataplane/overlay/journal/recovery loads.
  - **C1.b:** define Core-only, Base and Pro steady/burst/degraded workloads without assuming silicon or offload.
- **C2 — CPU accounting** [DOCUMENTED]
  - **C2.a:** define CPU core-equivalents, measurement of softirq/kernel/user, IRQ concentration and cost of WAN health/recovery.
  - **C2.b:** define sustained headroom, stress overload and decision to re-evaluate 1 Gbps MUST.
- **C3 — Memory budget** [DOCUMENTED]
  - **C3.a:** break down OS/network + five logical blocks, journal buffers, workload allocations and recovery reserve.
  - **C3.b:** calculate candidate Base/Pro PoC memory fixtures; measure actual conntrack per-entry and reclaimable caches.
- **C4 — Isolation and degradation** [DOCUMENTED]: reserve P0/P1/Core and enforce pressure-triggered workload shed/rejection before Core OOM.
- **C5 — Verification handoff** [DOCUMENTED]: measurable CPU/RAM trials with workload, WAN, cloud, power and crash pressure; evidence fields and falsification criteria.

**DoD design:** candidate arithmetic auditable, Base/Pro resource test profiles explicit, no hardware selection, open risks listed. **Result:** [06 § W1.5.C](../06-resource-envelope.md). **DoD validation:** W1.7 tests + W1.8 candidate hardware measurements, pending.

## W1.5.D — Storage Envelope

**State:** PLANNED. **Depends on:** A, C, persistence contract W1.2.

- **D1 — Volume model**
  - **D1.a:** instrument representative event payload-size percentiles and indexing/write amplification.
  - **D1.b:** compute 72h MUST-proposed and 7-day TARGET backlogs per profile; no fixed GB before D1.a.
- **D2 — Failure-safe storage:** define P0/P1 reserved capacity, known-good + dual-image/update space, P2/P3 quotas and secure identity storage (mechanism TBD).
- **D3 — Durability semantics**
  - **D3.a:** define append/commit/ACK, cursors and backpressure at full disk.
  - **D3.b:** specify abrupt power-cut, corruption, fsync/IOPS and recovery tests.
- **D4 — Endurance/lifecycle:** capacity, write-rate, retention, SSD/eMMC endurance and migration assumptions with uncertainty.
- **D5 — Storage gate:** size ranges Base/Pro, pressure policies and reproducible benchmark handoff.

**Output:** docs/06 D section + updated risks. **Acceptance:** P0/P1 protected, no ACK of undurable event; storage sizing explicitly bounded.

## W1.5.E — Workload Resource Model

**State:** PLANNED. **Depends on:** C/D and workload contracts.

- **E1 — Workload manifest**
  - **E1.a:** CPU/memory requests and limits; storage classes, capabilities, offline category.
  - **E1.b:** network intents declarative and privilege boundaries.
- **E2 — Admission lifecycle:** ADMIT/REJECT/DEGRADED on physical and logical limits; avoid overcommit of Core reserve.
- **E3 — Pressure and isolation:** quotas, OOM behavior, noisy-neighbor, restart/backoff and journal flood policy.
- **E4 — Contract tests:** lightweight, hostile/CPU hog, Host integrations and NVR-like synthetic profiles.

**Output:** docs/05 contract refinement and docs/06 resource policy; no implementation assumption. **Acceptance:** failure or rejection does not disable local PEF Core.

## W1.5.F — Power & Thermal Envelope

**State:** PLANNED. **Depends on:** C/D/E.

- **F1 — Power model:** idle/steady/peak W by Core, WAN adapter and optional disk/modem; isolate external radio/AP load.
- **F2 — Thermal envelope:** ambient range, throttle observation, cooling/fanless vs assisted cooling; no unsupported fanless claim.
- **F3 — UPS/power resilience:** interruption/brownout and minimum runtime scenarios; optional auxiliary power unit.
- **F4 — Verification:** energy-per-service, boot/recovery energy, throttling under routing + journaling + workloads.

**Output:** docs/06 F + trade-offs. **Acceptance:** candidate limits defined with measurement procedure, no product-specific power promise.

## W1.5.G — Recovery Performance Targets

**State:** PLANNED. **Depends on:** B/D/F and W1.2 failure gates.

- **G1 — Clock and event model**
  - **G1.a:** define failure `t0`, detection, action, restored service `t1`, stability window.
  - **G1.b:** define steady vs degraded workload and WAN upstream failure with carrier-up.
- **G2 — Targets:** candidate p50/p95/p99 for WAN failover, cloud reconcile, workload restart, boot, config/OTA rollback, journal drain; separate MUST/TARGET.
- **G3 — Regression controls:** false-positive failover, flapping, bounded retries, local service survivability and P1 evidence.
- **G4 — Harness handoff:** sample sizes, pass/fail, run artifacts, faults injected and confounders.

**Output:** docs/06 G and W1.7 harness requirements. **Acceptance:** every number has an observable `t0/t1` and a repeatable scenario.

## W1.5.H — Base vs Pro Matrix

**State:** PLANNED. **Depends on:** B–G.

- **H1 — Comparison:** consolidate minimum candidate, TARGET and STRESS for CPU/RAM/network/storage/power/recovery.
- **H2 — Sensitivity:** estimate savings/risks of one PoC device simulating two envelopes; no simulated power/BOM claims.
- **H3 — Decision register:** list discrepancies, accepted compromises, unknowns, W1.8 questions.

**Output:** one compact docs/06 comparison. **Acceptance:** no number without origin/uncertainty.

## W1.5.I — Hardware-agnostic Constraints

**State:** PLANNED. **Depends on:** H.

- **I1 — Capability constraints:** NIC count/speed, WAN-adapter pathways, trust/boot, persistence and expansion.
- **I2 — Feasibility filters:** CPU packet-processing/overlay benchmarks, memory reserve, storage durability and thermal envelope.
- **I3 — Shootout handoff:** objective mandatory/desirable trade-offs and test methodology for ARM router/edge, low-power x86 and split.

**Output:** testable constraints document, no vendor chosen. **Acceptance:** criteria can reject hardware based on evidence.
